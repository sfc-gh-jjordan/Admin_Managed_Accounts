Registering a New Managed Account

For an installation that is already running: connect one additional managed account to the Managed Accounts Admin app

Account registration guide — v1.0 — November 24, 2026
This guide covers only adding an account to an existing deployment. For the full install (central setup, worker, tasks, Streamlit app, admin duties), see the Deployment Guide.

Before you start: set an ACCOUNT_ID variable in your head (or notes). It is the short key in CONTROL.CUSTOMER_ACCOUNTS (for example CPG_ACME) and it appears in the secret, EAI, and worker procedure names. Use a distinct key pair per account. Nothing can be executed against the account until it passes preflight and is enabled.

Prerequisites

  • The app is already deployed (scripts 01–07 run, tasks created).
  • The worker code (sqlapi_client.py, actions.py, worker.py) is already on ACCT_ADMIN_DB.WORKER.CODE_STAGE. Check with LIST @ACCT_ADMIN_DB.WORKER.CODE_STAGE;. If it is empty, upload the three files first (see Deployment Guide 6.3).
  • A user with ORGADMIN (or GLOBALORGADMIN) and the ACCT_ADMIN_OWNER role for step 1; ACCT_ADMIN_BOOTSTRAP for steps 5–6; ACCT_ADMIN_WORKER for step 7.
  • ACCOUNTADMIN in the new managed account (or a delegate), with an approved change record.
  • openssl on your workstation.
  • Network path from EIGHTY451 to the new account (public HTTPS, or confirm Private Link / account-level network policy allowances first).

0. Create the Snowflake account (only if it does not exist yet)

EIGHTY451 Skip this step if the account is already in your organization.

USE ROLE ORGADMIN;
CREATE ACCOUNT EIGHTY451_ACME_EXT
  ADMIN_NAME = <admin_user>
  ADMIN_RSA_PUBLIC_KEY = '<key>'   -- or ADMIN_PASSWORD, per your standard
  EMAIL = '<admin_email>'
  EDITION = ENTERPRISE
  REGION = <snowflake_region>;
Naming matters. Discovery (step 1) only picks up accounts that match the SHOW ACCOUNTS LIKE pattern in sql/03 (default 'EIGHTY451%_EXT'). Name the account to match, or edit the pattern. The registry ACCOUNT_ID is derived from the account name (uppercased, non-alphanumerics replaced by _).

1. Discover and register the account

EIGHTY451 Run sql/03_org_account_discovery.sql as a user holding both ORGADMIN and ACCT_ADMIN_OWNER (the script runs USE SECONDARY ROLES ALL).

It lists accounts matching the pattern, excludes EIGHTY451 itself, and merges them into CONTROL.CUSTOMER_ACCOUNTS. The new account is inserted with:

  • IS_ENABLED = FALSE and BOOTSTRAP_STATUS = 'NOT_BOOTSTRAPPED'
  • Derived SQL_API_HOST (lowercase, _ → -) and JWT_ACCOUNT_IDENTIFIER (ORG-ACCOUNT, uppercase)
  • Pre-filled SECRET_NAME, WORKER_PROCEDURE, EAI_NAME following the naming convention

Existing accounts are only touched for descriptive fields, so re-running is safe.

Check: 
SELECT ACCOUNT_ID, ACCOUNT_LOCATOR, REGION, SQL_API_HOST, JWT_ACCOUNT_IDENTIFIER, BOOTSTRAP_STATUS, IS_ENABLED
FROM ACCT_ADMIN_DB.CONTROL.CUSTOMER_ACCOUNTS
WHERE BOOTSTRAP_STATUS = 'NOT_BOOTSTRAPPED';   -- your new account is listed
Note the ACCOUNT_ID; it is used in every step below. Correct DISPLAY_NAME if needed.

2. Generate a key pair

Workstation

ACCT=CPG_ACME   # the ACCOUNT_ID from step 1
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out sqlapi_${ACCT}.p8 -nocrypt
openssl rsa -in sqlapi_${ACCT}.p8 -pubout -out sqlapi_${ACCT}.pub
The .p8 file is a credential. It goes only into the Snowflake secret in step 5; delete it from the workstation afterward. Never commit it to source control or paste it into a chat or ticket.

3. Get the central egress IP ranges

EIGHTY451 The managed account only accepts the service user from EIGHTY451’s egress addresses.

SELECT value:"ipv4_prefix"::VARCHAR  AS ip_cidr_range,
       value:"effective"::TIMESTAMP  AS effective_date,
       value:"expires"::TIMESTAMP    AS expiration_date
FROM TABLE(FLATTEN(INPUT => PARSE_JSON(SYSTEM$GET_SNOWFLAKE_EGRESS_IP_RANGES())));

Copy the ip_cidr_range values as a quoted, comma-separated list, for example '20.1.2.0/28', '20.1.3.0/28'.

4. Bootstrap the managed account

Managed account Sign in to the new account as ACCOUNTADMIN. Confirm with SELECT CURRENT_ACCOUNT(); that you are not in EIGHTY451.

Open sql/04_target_account_bootstrap.sql and make two edits before running:

  1. Replace <<PASTE PUBLIC KEY BODY WITHOUT BEGIN/END LINES>> with the body of sqlapi_${ACCT}.pub (no BEGIN/END lines, no line breaks).
  2. Replace <<central egress CIDRs>> with the list from step 3.

Review the output of SHOW AUTHENTICATION POLICIES ON ACCOUNT; (never weaken a stronger existing policy), then run the script. It creates:

  • Database ADMIN_POLICIES with authentication policies CPG_HUMAN_MFA_V1, INTERNAL_ADMIN_MFA_V1 (password + required MFA) and SQLAPI_SERVICE_V1 (key pair only).
  • Network rule CENTRAL_EGRESS and network policy SQLAPI_SERVICE_NP, attached to the service user.
  • Service user SVC_ACCT_ADMIN (TYPE = SERVICE) with ACCOUNTADMIN and the optional ACCT_USER_ADMIN role.
CREATE NETWORK RULE and CREATE NETWORK POLICY in this script have no IF NOT EXISTS. Run it once per account; a second full run fails at that point.

Record from the final output:

  • RSA_PUBLIC_KEY_FP from DESC USER SVC_ACCT_ADMIN; (starts with SHA256:).
  • CURRENT_ACCOUNT() – must equal the ACCOUNT_LOCATOR in the registry.

The script does not pre-create customer roles (section 6 is commented out). Either create them now and add them to the role catalog in step 8, or let a CSV import create them on approval (requires EXEC_ROLE = ACCOUNTADMIN).

5. Store the private key and fingerprint

EIGHTY451 In a worksheet, as ACCT_ADMIN_BOOTSTRAP. Replace CPG_ACME in the secret name and the WHERE clause with your ACCOUNT_ID.

USE ROLE ACCT_ADMIN_BOOTSTRAP;
USE DATABASE ACCT_ADMIN_DB;

CREATE OR REPLACE SECRET ACCT_ADMIN_DB.SECRETS.SQLAPI_KEY_CPG_ACME
  TYPE = GENERIC_STRING
  SECRET_STRING = '-----BEGIN PRIVATE KEY-----
...contents of sqlapi_CPG_ACME.p8...
-----END PRIVATE KEY-----'
  COMMENT = 'SQL API private key for CPG_ACME (v1)';

UPDATE ACCT_ADMIN_DB.CONTROL.CUSTOMER_ACCOUNTS
   SET PUBLIC_KEY_FP    = 'SHA256:...from step 4...',
       SECRET_VERSION   = 1,
       REGISTRY_VERSION = REGISTRY_VERSION + 1,
       UPDATED_AT       = CURRENT_TIMESTAMP()
 WHERE ACCOUNT_ID = 'CPG_ACME';
Now delete the key files from your workstation: rm sqlapi_${ACCT}.p8 (keep the .pub if you wish; it is not secret).

6. Register connectivity

EIGHTY451 The procedure already exists from the original install, so you only call it. In sql/05_account_connectivity.sql you can instead set MANAGED_ACCOUNT_ID and run STEP C, but do not re-run the script unnecessarily.

USE ROLE ACCT_ADMIN_BOOTSTRAP;
CALL ACCT_ADMIN_DB.WORKER.REGISTER_ACCOUNT_CONNECTIVITY('CPG_ACME');

For this account only, it creates a network rule allowing just its SQL API host, an external access integration bound to that rule and secret, the worker procedure WORKER.EXEC_<ACCOUNT_ID>, and the grants to ACCT_ADMIN_WORKER. The status becomes CONNECTIVITY_READY.

Check: 
SHOW PROCEDURES LIKE 'EXEC_CPG_ACME' IN SCHEMA ACCT_ADMIN_DB.WORKER;
SHOW EXTERNAL ACCESS INTEGRATIONS LIKE 'ACCT_ADMIN_EAI_CPG_ACME';

SELECT ACCOUNT_ID, BOOTSTRAP_STATUS, IS_ENABLED
FROM ACCT_ADMIN_DB.CONTROL.CUSTOMER_ACCOUNTS
WHERE ACCOUNT_ID = 'CPG_ACME';   -- expect CONNECTIVITY_READY
If the call fails with sqlapi_client.py not found, the worker code is missing from CODE_STAGE or was uploaded compressed. Re-upload with AUTO_COMPRESS=FALSE to the stage root and retry.

7. Run the preflight

EIGHTY451 The preflight signs in to the managed account and makes no changes. It confirms the locator, service user, and execution role match the registry.

USE ROLE ACCT_ADMIN_WORKER;
CALL ACCT_ADMIN_DB.WORKER.RUN_ACCOUNT('CPG_ACME', 'PREFLIGHT');
Expected: the result contains "ok": true and BOOTSTRAP_STATUS becomes VERIFIED. If it fails, see Troubleshooting.

You can also run the preflight later from the app: Account registry → select the account → Run preflight.

8. Enable and configure the account

Only after a successful preflight. Either run SQL:

UPDATE ACCT_ADMIN_DB.CONTROL.CUSTOMER_ACCOUNTS
   SET IS_ENABLED = TRUE
 WHERE ACCOUNT_ID = 'CPG_ACME' AND BOOTSTRAP_STATUS = 'VERIFIED';

or use the app. On the Account registry page, select the account and:

  1. Set the Execution role: ACCOUNTADMIN (needed for CSV-created roles and internal admin grants) or ACCT_USER_ADMIN (least privilege).
  2. Set approved email domains and protected users.
  3. Turn Enabled on and save.
  4. Add allowed roles to the role catalog (they must already exist in the managed account), or plan to let a CSV import create them.
  5. Click Reconcile now to load the current user population as unmanaged inventory.
Scheduled tasks (DISPATCH_TASK, RECONCILE_TASK) pick up the account automatically once it is VERIFIED, enabled, and not paused. No task changes are needed. To assign who can operate or approve for this account, add rows to ADMIN_AUTHORIZATIONS as described in Deployment Guide section 9.

9. Clean up and verify

  • sqlapi_<ACCOUNT_ID>.p8 deleted from the workstation; no private key in source control or query history.
  • Registry row shows BOOTSTRAP_STATUS = VERIFIED, IS_ENABLED = TRUE, PUBLIC_KEY_FP matching DESC USER SVC_ACCT_ADMIN in the managed account.
  • Account locator in the registry matches CURRENT_ACCOUNT() in the managed account.
  • Execution role, approved email domains, and protected users configured.
  • Role catalog populated (or CSV role creation understood and approved).
  • First reconcile completed and inventory is visible in the app.
  • Duties assigned in ADMIN_AUTHORIZATIONS for this account.
  • CIDR expiry dates from step 3 noted for periodic review of CENTRAL_EGRESS.
