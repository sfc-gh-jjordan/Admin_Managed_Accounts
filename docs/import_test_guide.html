CSV Import Testing Guide

Managed Accounts: adding, disabling, and changing users and roles with a CSV file

Overview

This guide explains how to test the CSV import process before you rely on it for real changes. The import lets an approved operator submit a file of user changes for one managed account. An approver then reviews and approves the batch before anything changes in the account.

The test files in docs/import_test_scenarios/ cover the main actions (add users, disable and re-enable users, add and replace roles, create new roles) and the checks that reject bad input. Each file has one purpose, so a failure points to one rule.

Run these tests in a sandbox managed account first. The sample data uses the account CPG_ACME and the approved email domain acmefoods.example. Replace the domain, role names, and existing usernames with the values for your own account before you run the files.

Before you start

  • You have operator permission on the test account in the admin app.
  • A different admin is available to approve batches. You cannot approve a batch you submitted.
  • The account's approved email domain list includes the domain used in the test files.
  • The roles used in the files (CPG_ANALYST, CPG_WRITER, ACME_PROMO_ANALYST) exist in the account's role catalog, or you have updated the files to use roles that do.
  • The existing users named in the files (JANE_SMITH, RAVI_PATEL, MAYA_CHEN, PAT_LEE, J_ORTIZ_8451, ACME_BREAKGLASS, LEGACY_ETL) match your account. Change them to your own users where needed.
  • You have a ticket or change reference to enter with each submission.

How an import works

  1. Upload. Choose the account in the Import and review page and upload the CSV.
  2. Review. Each row is checked. Valid rows show Valid. Rejected rows show Rejected with the reason in the Findings column.
  3. Exclude rejected rows. You must tick Exclude on every rejected row before the batch can be submitted. Excluded rows are not processed.
  4. Confirm new roles. If the file names a role that is not in the catalog, the page lists it under Roles to be created. Tick the confirmation before submitting.
  5. Submit. Enter a reason and a ticket reference, then select Submit for approval.
  6. Approve. A second admin reviews the batch in the Approval queue and approves it. Nothing changes in the account until approval.
  7. Execute. The changes are applied to the account and read back to confirm. Each operation shows as succeeded, failed, or blocked in the operations list.

CSV format

The header row must match exactly, in this order:

username,email,first_name,last_name,role_name,default_role,action
ColumnRule
usernameLetters, digits and underscores, starting with a letter, up to 128 characters. Stored in upper case. The same username in different letter cases in one file is rejected.
emailRequired for ONBOARD, ADD_ROLES and SET_MANAGED_ROLES. Must be a valid address on an approved domain for the account. Not used for DISABLE or REENABLE.
first_name, last_nameLetters, spaces, apostrophes, periods and hyphens only, up to 64 characters.
role_nameA role in the account's catalog, or a new role name (see below). Must be empty for DISABLE and REENABLE.
default_roleOptional. Must be one of the roles requested for that user in the same file, and must be default-eligible. Must be empty for DISABLE and REENABLE.
actionOne of ONBOARD, ADD_ROLES, SET_MANAGED_ROLES, DISABLE, REENABLE.

Limits: 1 MB, 2,000 data rows, and at most 10 new roles in one batch. The file must be UTF-8. Free text must not contain URLs, semicolons, SQL keywords, or the words password, secret, or private key. Rows for the same user must agree on email, first and last name, default role and action.

Some words are blocked in name and role fields even when they look harmless. If a valid-looking name is rejected for "forbidden content", check it for those words and for punctuation such as ; or --.

Actions

ActionWhat it doesTypical use
ONBOARDCreates the user (or updates a managed user) with the listed roles, default role, and enabled status.New starter
ADD_ROLESAdds the listed roles to an existing managed user. Other roles are kept.Extra access for an existing user
SET_MANAGED_ROLESReplaces the user's managed roles with exactly the roles listed. Roles not listed are removed.Align a user to a defined role set
DISABLEDisables the user. The user record and roles are kept.Leaver or temporary suspension
REENABLEEnables a previously disabled managed user.Return from suspension

Only users the admin app already manages can be changed with ADD_ROLES, SET_MANAGED_ROLES, DISABLE or REENABLE. Existing unmanaged users, protected users, and internal admin identities are never changed by a CSV.

Suggested run order

Some scenarios depend on the state left by earlier ones. Run them in this order on a sandbox account:

  1. Rejection checks first (files 07 to 17). They change nothing if the batch is not submitted.
  2. Valid onboarding (01), then the new-role onboarding (02).
  3. Role changes (05, 06), then disable and re-enable (03, 04).
  4. Mixed file (13) last, since it needs an exclusion step.

Files 03 and 04 use existing users, so they can run at any time. Do not run 03 for a user you still need to test with.
