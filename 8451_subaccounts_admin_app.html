84.51 CPG User Lifecycle Admin

Solution design for centrally managing human users across 150+ CPG customer Snowflake accounts

1. Purpose and scope

A Streamlit in Snowflake application running in 84.51’s main account (EIGHTY451) manages human users across more than 150 CPG customer accounts. These are full Snowflake accounts with read/write capability, not reader accounts.

Customer requests

CPG customers send CSV user and role requests. The app validates, stages, and routes them for admin approval.

Remote execution

Approved onboarding/offboarding is queued and executed through the Snowflake SQL API.

Central inventory

A single view of verified remote user status and assigned roles across all accounts.

Privileged access

Named 84.51 admins can be granted ACCOUNTADMIN on selected accounts via a separate, MFA-gated workflow.

Authentication: Customer users authenticate with native Snowflake passwords plus MFA. Customer SSO and SCIM are out of scope. Newly provisioned 84.51 administrators also use local PERSON users with password plus native MFA in the initial design.
This document describes a proposed design. It does not authorize account changes. Account identifiers, regions, and existing infrastructure will be verified before implementation; all table names are proposed.

2. Architecture

flowchart TD
  A[CPG-provided CSV] --> B["84.51 Streamlit app in EIGHTY451
Upload → Validate → Preview → Approve"]
  B --> C[Control tables & durable operation queue]
  C --> D[Scheduled Snowflake Task → Python worker procedure]
  D --> E[Account-scoped secret + external access integration]
  E --> F["Registered customer-account SQL API endpoint
Preflight → Execute → Verify → Record"]
  F --> G[Central inventory, reconciliation & audit history]
  • UI is separated from execution. The app never holds target private keys and does not need an open browser to finish a batch.
  • A scheduled worker picks up approved operations in bounded batches. Start with a single non-overlapping dispatcher; add account-sharded concurrency after pilot testing.
  • The Streamlit app (warehouse runtime baseline) reads central control data only. Target administration is performed through the SQL API using the target service identity.

3. Account registry and security boundary

An admin-controlled customer registry holds, per account:

  • Customer ID and display name.
  • Account locator, region/cloud, organization/account name, and verified HTTPS SQL API hostname.
  • Expected target account identity for preflight verification.
  • Service username, explicit execution role, and execution context.
  • Worker procedure and secret/credential version references — never key material.
  • Approved email domains, roles, protected users, and paused/enabled state.
  • Customer and internal-admin MFA policy names, expected versions, and bootstrap health.
  • Approved internal-admin roster references, privileged approvers, low-privilege default role, and emergency-access coverage.

An account locator alone is not sufficient connection configuration. Admins choose the customer/account from the registry; CSVs can never supply hosts, credentials, procedure names, SQL, or policy definitions. Each approved payload is bound to the registry and role-catalog versions to prevent redirection after approval.

5. CSV request contract

One row per user-role assignment. Repeated rows for a username must agree on identity, default role, and action.

username,email,first_name,last_name,role_name,default_role,action
JANE_SMITH,jane.smith@customer.example,Jane,Smith,CPG_ANALYST,CPG_ANALYST,ONBOARD
JANE_SMITH,jane.smith@customer.example,Jane,Smith,CPG_WRITER,CPG_ANALYST,ONBOARD
PAT_LEE,pat.lee@customer.example,Pat,Lee,,,DISABLE

Identities and roles shown are illustrative.

Validation rules

  • Strict headers, encoding, file-size and row-count limits.
  • Approved email domains, with a documented exception process.
  • Strict username conventions; reject case collisions and ambiguous identifiers.
  • Only existing roles from the account allowlist — roles are never created from CSV.
  • ACCOUNTADMIN and other privileged or non-compliant roles are always blocked in customer CSVs.
  • Service users, emergency admins, internal identities, and unknown existing users are protected.
  • Passwords, private keys, MFA seeds, SQL text, policy names, and URLs are rejected.
  • Uploaded values render as text; downloadable CSVs are protected against formula injection.
  • Files and normalized payloads are hashed for duplicate detection and approval integrity.

Import actions

ONBOARDAdditive and idempotent; replay never recreates users or resets credentials.
ADD_ROLESAdds approved role assignments.
SET_MANAGED_ROLES (optional)Replaces only app-managed grants after previewing removals; external grants preserved.

6. Application screens

Overview

Enabled/disabled managed users, pending approvals, handoff/MFA pending, failed operations, stale or drifted inventory. Managed coverage shown distinctly from total account population.

Import & review

Select account, upload CSV, inspect row errors, preview users, roles, disables, and policy impact. The whole batch is validated first; rejected rows require explicit exclusion.

Approval queue

Requester, approver, reason/ticket, customer confirmation, payload version. Second-admin approval recommended for bulk actions. Stale approvals rejected.

User inventory

Filter by account, user, lifecycle/operation/MFA status, and drift. Desired vs observed roles, policy, default role, and redacted history.

Internal admin access

Restricted to privileged operators/approvers. Roster-based selection, per-account ACCOUNTADMIN grant/revoke previews, review dates, MFA evidence.

Operations & health

Step-level results, API handles, retry eligibility, paused accounts, credential/network/policy failures. Refresh triggers reconciliation only.

7. Authentication policy baseline

Each customer account is bootstrapped through a separately approved process:

  • Dedicated local policy schema where needed.
  • Versioned customer-human policy: PASSWORD with MFA enrollment REQUIRED.
  • Prefer passkey and TOTP (subject to client testing); Duo only as an approved alternative.
  • Snowsight remains available for enrollment. Passkeys here act as second factors.
  • Customer policy attached directly to app-managed customer users for the MVP, avoiding unintended changes to internal humans and services.
  • Separate versioned internal-admin policy (PASSWORD + required native MFA; passkeys/security keys recommended). Unknown enrollment evidence blocks ACCOUNTADMIN grants. Existing stronger policies are never weakened.
  • Effective policies are inspected first (user-level overrides account-level); unexpected differences block rather than overwrite.
  • Administrative service key-pair access and tested emergency access are preserved.

Per-user attachment does not protect unmanaged users; coverage and drift are reported. Account-wide enforcement is a separate hardening change.

8. Onboarding workflow

  1. Claim an approved operation and verify version, target, and preconditions.
  2. Generate an account-specific key-pair JWT and verify account, service identity, and role.
  3. Inspect user existence, roles, and policy. Existing unknown users require explicit adoption approval.
  4. Ensure the customer policy exists and matches the approved version.
  5. Create the PERSON user initially disabled, with no centrally chosen password.
  6. Attach the policy, grant allowed roles, and grant the default role.
  7. Verify user type, policy, and grants before enabling.
  8. Generate a password-setup/reset link on explicit authorized request (flow piloted first).
  9. Initiate MFA enrollment; Snowflake emails verified addresses, otherwise an enrollment URL is returned for secure delivery.
  10. Record verified configuration; track provisioning, handoff, and MFA enrollment separately.
Password-reset links are single-use and expire after 12 hours. They are generated near delivery and never on import replay.

Sensitive handoff

The MVP uses a restricted admin workflow and an approved customer communication channel. Reset and enrollment links are never stored in ordinary audit tables, logs, exports, or caches. Customer MFA seeds and passkeys remain under customer control, and no confidential data is sent to unapproved external services.

9. Internal 84.51 ACCOUNTADMIN workflow

A separate trusted action family — not an exception to the customer CSV allowlist.

flowchart LR
  R[Roster validation] --> AP[Independent approval]
  AP --> V[Verify target & boundaries]
  V --> U[Create disabled PERSON user
+ admin MFA policy
+ low-privilege default]
  U --> H[Secure password & MFA handoff]
  H --> M{MFA enrollment
verified?}
  M -- No --> B[AWAITING_MFA / BLOCKED]
  M -- Yes --> G[Revalidate & grant ACCOUNTADMIN
directly to user]
  G --> REC[Record GRANTED + scheduled reconciliation]
  1. Validate the employee against the approved roster (verified corporate email and eligibility; a domain alone is insufficient).
  2. Require approval from another authorized approver — no self-approval. Approval is bound to person, exact accounts, reason, review/expiry, and versions.
  3. Verify target account, privileged worker identity, and protected-user boundaries. Never convert customer or service users.
  4. Create an initially disabled PERSON user with the internal-admin MFA policy and a low-privilege default role (never ACCOUNTADMIN).
  5. Complete secure password setup and MFA enrollment; ACCOUNTADMIN is not yet granted.
  6. Confirm actual MFA enrollment; a required policy or sent invitation alone does not satisfy the gate.
  7. Revalidate immediately before granting ACCOUNTADMIN directly to the user, then verify remotely.
  8. Record GRANTED state with evidence and review/expiry date. The admin selects ACCOUNTADMIN explicitly in Snowsight when needed.
  9. Reconcile grants and policy drift on a schedule; unauthorized or expired grants are raised for revocation (expiry is application-enforced).

Revocation and employee offboarding

  • REVOKE_ACCOUNTADMIN removes only the privileged grant.
  • DISABLE_INTERNAL_ADMIN disables the user in selected accounts and verifies the outcome.
  • Departures are reconciled against every managed-account assignment, including partial failures.
  • Before removal, remaining human-admin and emergency coverage is checked (Snowflake recommends at least two ACCOUNTADMIN users, never as default role). Emergency disabling of a compromised identity is never silently blocked; overrides are recorded and alerted.
  • Ownership or other grants may remain after revocation and are handled through explicit approved cleanup.

10. Offboarding workflow

  1. Select users or upload explicit DISABLE requests; record account, reason, and approval.
  2. Set desired state to DISABLED and queue the action.
  3. Verify the target is an app-managed customer human, not a protected identity.
  4. Disable the user via the target SQL API.
  5. Read back remote state and record verified disablement.
  6. Retain user/role history; users are not dropped by default. Role revocation is a separate optional step.

Already-disabled users report verified success; absent users show NOT_FOUND; unreachable accounts remain pending with stale/unknown observation. Disabling a user blocks login and new queries and aborts running/scheduled queries; existing-session behavior is validated during the pilot.

11. Reliable SQL API execution

  • Short-lived key-pair JWTs with correct account/user canonicalization and fingerprint.
  • Regional endpoint hostname kept separate from JWT account identity.
  • Explicit execution role on every request; one bounded step per request with durable request UUID and statement handle.
  • Asynchronous completion and result partitions handled.
  • Documented resubmission semantics with preserved request IDs; credential issuance is never blindly replayed.
  • Target state re-read when outcomes are uncertain; resume from verified steps.
  • Conflicting account/user actions serialized; a newer disable supersedes stale onboarding work.
  • Bounded polling, retries/backoff, circuit breakers, and per-account pause controls.
  • Fixed SQL action templates with bindings and validated/quoted identifiers.
  • Registered HTTPS destinations only, TLS verification, no cross-host redirects.

12. Roles, credentials, and network controls

  • Dedicated app-owner, viewer, operator, approver, bootstrap, and worker roles. The UI owner does not hold ACCOUNTADMIN or read target secrets.
  • Viewer identity via st.user.user_name; authorization enforced in trusted command paths and revalidated by the worker.
  • Target service user with a narrow custom role for user management, allowed role grants, and policies. The ordinary worker cannot grant ACCOUNTADMIN.
  • A separate privileged worker and credential path handles internal-admin grants/revocations, with narrow permissions, fixed actions, per-account approvals, and monitoring.
  • Independent per-account keys stored in Snowflake secret objects; narrow external access integrations.
  • Target network policies verified to admit the worker path; connectivity (public or private) tested before deployment.
  • Keys, JWTs, passwords, MFA seeds, and credential links never appear in source, inventory, logs, or exports.

13. Reconciliation

Scheduled and on-demand read-only checks verify user existence/type, disabled flag, direct grants, defaults, policy version, and available MFA enrollment evidence, using immediate metadata rather than delayed usage views.

Reconciliation detects drift by default; it does not silently revoke grants, repair policies, or re-enable users. For internal admins it also verifies ACCOUNTADMIN grants, roster eligibility, approval validity, default roles, MFA evidence, and emergency coverage.

14. Acceptance tests

  • CSVs cannot redirect accounts, inject SQL, target protected users, or bypass role restrictions.
  • Policy attachment precedes activation; administrative key-pair access remains intact.
  • Password setup and MFA enrollment work with Snowsight and actual customer clients.
  • Duplicate uploads and UI reruns do not duplicate provisioning or reset links.
  • Browser closure does not stop execution.
  • Expired JWTs, permission failures, timeouts, async responses, and result partitions are handled.
  • Partial remote execution and failed central writes reconcile safely.
  • Concurrent disable/onboard actions cannot re-enable through stale work.
  • Offboarding is remotely verified before central completion.
  • Unknown, absent, stale, MFA-required, and enrolled states remain distinct.
  • Attribution, secret isolation, sensitive handoff, and retention are tested.
  • Customer CSVs, ordinary operators, and ordinary worker credentials cannot grant ACCOUNTADMIN.
  • Internal-admin grants require roster eligibility, independent approval, verified MFA, and remote verification.
  • Internal admins default to a lower-privilege role; revocation and disablement remain distinct.
  • Expiry enforcement, cross-account departures, partial revocation failures, and emergency overrides are tested.
